# Insurance Claims API Reference

This reference describes the current claims and covers endpoints. Controllers dispatch MediatR requests; handlers call services, map responses, and enqueue audit records for successful writes.

## Connection and Format

- Local project launch profile: `https://localhost:7052` (HTTP listener: `http://localhost:5052`). HTTP requests may be redirected to HTTPS.
- Route prefix: `/api`.
- Request and response format: JSON with camelCase property names. Send `Content-Type: application/json` for JSON bodies.
- Dates: ISO 8601, for example `2026-10-13T00:00:00Z`. Creation timestamps are generated by the server in UTC.
- Enums are serialized as strings. Use the names listed below in JSON and query parameters.
- No authentication or authorization requirement is currently configured for these endpoints.
- Swagger UI is available at `/swagger` in Development; the OpenAPI document is at `/swagger/v1/swagger.json`.

Example dates and IDs in this document are illustrative. Replace them with dates valid at the time of the request and IDs returned by the API. Create a currently active cover before creating a claim.

## Endpoint Summary

| Method | Route | Operation | Success | Service-level failure |
| --- | --- | --- | --- | --- |
| GET | `/api/claims` | List claims | 200 | Not applicable |
| GET | `/api/claims/{id}` | Get claim | 200 | 400 when missing |
| POST | `/api/claims` | Create claim | 201 | 400 |
| PUT | `/api/claims/{id}` | Update claim | 202 | 400 |
| DELETE | `/api/claims/{id}` | Delete claim | 200 | 400 |
| GET | `/api/covers` | List covers | 200 | Not applicable |
| GET | `/api/covers/{id}` | Get cover | 200 | 404 when missing |
| POST | `/api/covers` | Create cover | 201 | 400 |

| POST | `/api/covers/compute` | Compute premium without saving | 200 | See computation caveats below |

IDs are strings generated as GUIDs by the server. Path parameters are not restricted to a GUID format. There are no pagination, filtering, or sorting parameters on the list endpoints.

## Response Envelope

Handler responses use `ResponseModel<T>`. The actual HTTP status matches the `statusCode` field.

```json
{
  "statusCode": 200,
  "success": true,
  "message": "Success",
  "data": null,
  "errors": []
}
```

`data` contains a resource, an array of resources, a numeric premium, or `null`, depending on the endpoint. Successful updates return `null`, while successful deletes return the deleted resource.

Service validation messages are preserved in `message`. These failures currently leave `errors` empty:

```json
{
  "statusCode": 400,
  "success": false,
  "message": "DamageCost cannot exceed 100,000.",
  "data": null,
  "errors": []
}
```

Malformed JSON, invalid enum names, missing required values, and other MVC binding/validation errors can return HTTP 400 with ASP.NET Core `ValidationProblemDetails` instead of this envelope. Unhandled exceptions are not mapped to `ResponseModel<T>` and may return HTTP 500.

## Claims Endpoints

### GET /api/claims

Returns all claims. No request body or query parameters.

```http
GET /api/claims
Accept: application/json
```

Response: HTTP 200, with `data` containing an array of Claim resources. An empty collection returns `data: []`.

### GET /api/claims/{id}

Returns one claim. Required path parameter: `id` (string).

```http
GET /api/claims/c010ea0c-9a34-4a77-93f9-c380f916e641
Accept: application/json
```

Response: HTTP 200 with a Claim resource in `data`.

Missing claim: HTTP 400, `success: false`, `message: "Claim not found"`, `data: null`. This endpoint currently does not use HTTP 404.

### POST /api/claims

Creates a claim against an existing cover. Request body:

```json
{
  "coverId": "a324ad15-dcb2-4ddd-a867-79cf93e63a41",
  "name": "Engine fire",
  "type": "Fire",
  "damageCost": 25000
}
```

`coverId`, `name`, `type`, and `damageCost` map to `CreateClaimDto`. The server generates `id` and `dateCreated`; these fields are not inputs.

Response: HTTP 201 with the created Claim resource in `data`. No `Location` header is currently generated.

Validation failures return HTTP 400:

- `Cover not found.`
- `DamageCost cannot exceed 100,000.`
- `Claim creation date must be within the related cover period.`

The cover must include the current UTC creation timestamp. Successful creation enqueues a Claim POST audit record.

### PUT /api/claims/{id}

Updates the editable fields of an existing claim. Required path parameter: `id` (string). Request body:

```json
{
  "name": "Revised engine fire",
  "type": "Fire",
  "damageCost": 30000
}
```

This is an update of all editable fields, not a PATCH operation. `coverId`, `id`, and `dateCreated` cannot be changed through this DTO.

Response: HTTP 202, `success: true`, `data: null`. The service has already saved the update when this response is returned; the status does not mean the update is queued for later execution.

Failures return HTTP 400:

- `Claim not found.`
- `Related cover not found.`
- `DamageCost cannot exceed 100,000.`
- `Claim creation date must be within the related cover period.`

Validation uses the claim's original creation timestamp, not the update time. Successful update enqueues a Claim PUT audit record.

### DELETE /api/claims/{id}

Deletes a claim. Required path parameter: `id` (string). No request body.

```http
DELETE /api/claims/c010ea0c-9a34-4a77-93f9-c380f916e641
```

Response: HTTP 200 with the deleted Claim resource in `data`.

Missing claim: HTTP 400 with `message: "Claim with ID '<id>' was not found."`. Successful deletion enqueues a Claim DELETE audit record.

## Covers Endpoints

### GET /api/covers

Returns all covers. No request body or query parameters.

```http
GET /api/covers
Accept: application/json
```

Response: HTTP 200, with `data` containing an array of Cover resources. An empty collection returns `data: []`.

### GET /api/covers/{id}

Returns one cover. Required path parameter: `id` (string).

```http
GET /api/covers/a324ad15-dcb2-4ddd-a867-79cf93e63a41
Accept: application/json
```

Response: HTTP 200 with a Cover resource in `data`.

Missing cover: HTTP 404, `success: false`, `message: "Not found"`, `data: null`.

### POST /api/covers

Creates a cover and computes its premium. Request body:

```json
{
  "startDate": "2026-10-13T00:00:00Z",
  "endDate": "2026-11-12T00:00:00Z",
  "type": "Yacht"
}
```

`startDate`, `endDate`, and `type` map to `CreateCoverDto`. The server generates `id`, `dateCreated`, and `premium`; these fields are not inputs.

Response: HTTP 201 with the created Cover resource in `data`. No `Location` header is currently generated.

Validation failures return HTTP 400:

- `StartDate cannot be in the past.`
- `EndDate cannot be earlier than StartDate.`
- `The insurance period cannot exceed one year.`

Successful creation enqueues a Cover POST audit record.

### PUT /api/covers/{id}

Updates cover dates and type, then recalculates the premium. Required path parameter: `id` (string). Request body:

```json
{
  "startDate": "2026-10-13T00:00:00Z",
  "endDate": "2026-12-12T00:00:00Z",
  "type": "Tanker"
}
```

This is an update of all editable fields, not a PATCH operation. `id`, `dateCreated`, and `premium` cannot be directly changed through this DTO.

Response: HTTP 202, `success: true`, `data: null`. The update has already been saved; retrieve the cover to obtain the new premium.

Failures return HTTP 400 with `Cover not found.` or one of the cover date validation messages listed for creation. These validations also apply to updates, so submitting an unchanged start date that is now in the past fails validation.

Successful update enqueues a Cover PUT audit record. The current service does not revalidate existing claims against the changed cover dates.

### DELETE /api/covers/{id}

Deletes a cover. Required path parameter: `id` (string). No request body.

```http
DELETE /api/covers/a324ad15-dcb2-4ddd-a867-79cf93e63a41
```

Response: HTTP 200 with the deleted Cover resource in `data`.

Missing cover: HTTP 400 with `message: "Cover not found."`. Successful deletion enqueues a Cover DELETE audit record. The service does not explicitly delete related claims or block deletion when claims exist.

### POST /api/covers/compute

Computes a premium without creating or updating a cover. Inputs are query parameters, not a JSON body.

| Parameter | Type | Description |
| --- | --- | --- |
| `startDate` | DateTime | Start date in ISO 8601 format |
| `endDate` | DateTime | End date in ISO 8601 format |
| `coverType` | CoverType | Covered object type; parameter name differs from the DTO's `type` |

```http
POST /api/covers/compute?startDate=2026-10-13&endDate=2026-11-12&coverType=Yacht
Accept: application/json
```

Response: HTTP 200, with the numeric premium in `data`:

```json
{
  "statusCode": 200,
  "success": true,
  "message": "Success",
  "data": 41250,
  "errors": []
}
```

This operation does not enqueue an audit record. It does not enforce the cover creation rules about past start dates or the one-year limit. An end calendar date before the start calendar date throws an `ArgumentException`; there is currently no handler mapping that exception to HTTP 400, so it can produce HTTP 500.

## Premium Calculation

Insured days are `(endDate.Date - startDate.Date).Days`. Time-of-day is ignored, the end date is excluded, and a same-calendar-day period costs zero. No currency or explicit rounding rule is currently defined.

The base daily rate is 1250, adjusted by cover type:

| Cover type | Multiplier | Initial daily rate |
| --- | --- | --- |
| Yacht | 1.10 | 1375 |
| PassengerShip | 1.20 | 1500 |
| ContainerShip | 1.30 | 1625 |
| BulkCarrier | 1.30 | 1625 |
| Tanker | 1.50 | 1875 |

Discounts apply progressively to the days in each tier, not retroactively to the whole period:

| Tier | Days | Yacht discount | Other types discount |
| --- | --- | --- | --- |
| Initial | First 30 | 0% | 0% |
| Discounted | Next 150 (days 31-180) | 5% | 2% |
| Remaining | Days after 180 | 8% total | 3% total |

The final tier adds 3 percentage points for Yacht and 1 percentage point for other types to the previous discount; discounts are not compounded. For a 31-day Yacht period, the premium is `30 * 1375 + 1 * 1306.25 = 42556.25`.

## Date Validation and Auditing

- Claim damage cost may equal 100,000 but cannot exceed it. No lower-bound damage-cost validation is currently implemented.
- Claim creation is validated using the exact UTC timestamp stored in `dateCreated`. Both cover boundaries are inclusive for this validation.
- Claim updates check that original timestamp against the related cover's current dates.
- Cover start validation compares `startDate.Date` with the server's local `DateTime.Today`, so earlier times today are allowed.
- Cover end validation compares exact timestamps. End must not precede start or exceed `startDate.AddYears(1)`. Exactly one calendar year is permitted; leap years are handled by `AddYears`.
- Claim-period validation uses timestamps, unlike the calendar-day premium formula. A cover ending at midnight does not include claims later that day. Use consistent time-zone conventions when supplying cover dates.
- Successful create, update, and delete handlers enqueue an audit record to an in-memory channel after persistence. A background worker writes audits separately. The queue is not durable, and returning a response does not guarantee that the audit has already reached its database.
- Queries, premium computation, and service validation failures do not enqueue audit records.
